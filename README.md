# msi-diff

Generated by AI (Cursor Grok 4.6).

Command-line comparison of two MSI packages with a report in HTML and/or Markdown.

The tool reads Windows Installer databases directly through `msi.dll`, so there are
**no external dependencies**: all you need is Windows with Windows PowerShell 5.1
(part of the OS since Windows 7 SP1 / Server 2008 R2). WiX, Orca or InstEd are not
required.

A pair of 200 MB packages with 15,000 table rows is compared in roughly 15 seconds;
small packages take a couple of seconds.

## Quick start

```powershell
.\Compare-Msi.ps1 .\app-1.0.msi .\app-1.1.msi
```

The report is written to `.\msi-diff.html` and a short summary is printed to the
console.

From `cmd.exe`:

```bat
msi-diff.cmd app-1.0.msi app-1.1.msi -MarkdownReport diff.md
```

## What is compared

| Report section | Data source |
| --- | --- |
| Summary Information Stream | package metadata: PackageCode, Template (platform and languages), schema version, source flags, security |
| `Property` table | ProductCode, ProductVersion, UpgradeCode, Manufacturer and the rest |
| Installed files | `File` + `Component` + `Directory` + `MsiFileHash` flattened into target paths with versions, sizes and MD5 |
| Every database table | row-by-row comparison by primary key, including added and removed tables and columns |

Binary streams (the `Binary` and `Icon` tables and any OBJECT column) are compared by
size and by the SHA-256 of their contents, so a swapped custom action DLL does not go
unnoticed.

## Parameters

| Parameter | Purpose |
| --- | --- |
| `-ReferenceMsi` (pos. 0) | the original package, left-hand side of the comparison |
| `-DifferenceMsi` (pos. 1) | the new package, right-hand side |
| `-HtmlReport <path>` | path to the HTML report |
| `-MarkdownReport <path>` | path to the Markdown report |
| `-IncludeTable <names>` | compare only these tables, wildcards supported: `File`, `Msi*` |
| `-ExcludeTable <names>` | exclude tables, wildcards supported: `_Validation`, `Msi*` |
| `-IgnoreProperty <names>` | ignore differences in the given `Property` entries |
| `-IgnoreBuildNoise` | ignore what every rebuild changes: PackageCode, ProductCode, timestamps, LastSavedBy, CreatingApplication |
| `-SignificantOnly` | significant changes only: ignore file size, version and checksums, the version bounds in `Upgrade`, the `ProductCode` and `ProductVersion` properties and the summary `Comments` field |
| `-MaxRowsPerTable <n>` | maximum differing rows per table in the report, 500 by default, `0` means unlimited |
| `-NoStreamHash` | do not hash binary streams (faster on packages with a large `Binary` table) |
| `-ShowUnchanged` | include identical rows and tables in the report |
| `-OpenReport` | open the HTML report once it is written |
| `-PassThru` | return the comparison object to the pipeline for further processing |
| `-Quiet` | do not print the summary to the console |

If neither `-HtmlReport` nor `-MarkdownReport` is given, `.\msi-diff.html` is used.

### Significant changes only

`-SignificantOnly` answers "did the content and structure of the package change?"
rather than "were the binaries rebuilt and the version bumped?". In this mode the
following is excluded from the comparison:

| What | Where |
| --- | --- |
| file size | `File.FileSize` and the `Size` column of the file view |
| file version | `File.Version` and the `Version` column of the file view |
| checksum | `MsiFileHash.HashPart1..4` and the `MD5` column of the file view |
| upgrade version bounds | `Upgrade.VersionMin` and `Upgrade.VersionMax` |
| product identity | the `ProductCode` and `ProductVersion` properties of the `Property` table |
| package description | the `Comments` field of the Summary Information Stream |

Everything else is still taken into account: added, removed and moved files, a changed
component or sequence, and changes to the registry, shortcuts, components, features,
custom actions and properties. Streams in the `Binary` and `Icon` tables are still
compared as well - that is custom action code, not installation payload.

`VersionMin` and `VersionMax` are part of the primary key of the `Upgrade` table, so in
this mode they are dropped from the row matching key too: otherwise a shifted version
bound would turn into a removed/added pair instead of being ignored. `Upgrade` rows are
then matched by `UpgradeCode`, `Language` and `Attributes`, which is enough to tell
apart the rules WiX generates for detecting an older and a newer version. The effective
match key and the list of excluded columns are printed next to every table in the
report, so the mode is always visible from the report itself.

`ProductCode` and `ProductVersion` are excluded as whole rows, both in the dedicated
"Property table" section and in the generic comparison of the `Property` table. The
list of excluded rows is printed next to the table as well.

`Comments` is dropped from the Summary Information Stream because build tools usually
fill it with the product name and version, so it changes on every release without
saying anything about the content of the package.

If the packages differ **only** in the items listed above, the verdict is "the packages
are identical" and the exit code is 0. The mode combines with `-IgnoreBuildNoise`.

## Exit codes

| Code | Meaning |
| --- | --- |
| 0 | the packages are identical |
| 1 | differences found |
| 2 | error (file not found, not an MSI database, and so on) |

Handy for CI: the build fails when a new package unexpectedly diverges from the
baseline.

## Examples

Comparing two builds of the same product while ignoring what always changes:

```powershell
.\Compare-Msi.ps1 -ReferenceMsi .\build-100\app.msi -DifferenceMsi .\build-101\app.msi `
    -HtmlReport .\out\diff.html -MarkdownReport .\out\diff.md `
    -IgnoreBuildNoise -OpenReport
```

Checking whether the content of the package changed, without reacting to rebuilt
binaries:

```powershell
.\Compare-Msi.ps1 .\release-1.4.0.msi .\release-1.4.1.msi `
    -SignificantOnly -IgnoreBuildNoise -MarkdownReport .\out\structure.md
```

Files and components only, with no row limit:

```powershell
.\Compare-Msi.ps1 old.msi new.msi -IncludeTable File,Component,Directory,MsiFileHash -MaxRowsPerTable 0
```

A quick gate in a build pipeline:

```powershell
.\Compare-Msi.ps1 $baseline $candidate -MarkdownReport report.md -IgnoreBuildNoise -Quiet
if ($LASTEXITCODE -eq 1) { Write-Warning 'Package differs from the baseline, see report.md' }
```

Working with the comparison result directly:

```powershell
$diff = .\Compare-Msi.ps1 old.msi new.msi -PassThru -Quiet
$diff.FileDiff.ChangedRows | ForEach-Object { $_.Reference.TargetPath }
```

## HTML report

A single self-contained file with no external resources: attach it to a ticket or
publish it as a build artifact. Inside are summary cards, a filter box that matches
every row of the report, a "differences only" toggle, collapsible per-table sections
and old/new highlighting inside changed cells. The theme follows the system light or
dark preference.

## Markdown report

GitHub-flavoured: summary tables, changed values rendered as `**old** -> **new**`, and
row-level differences tucked into `<details>` blocks so that a long report stays
readable in a pull request or issue description.

## Project layout

```
Compare-Msi.ps1            CLI entry point
msi-diff.cmd               wrapper for running from cmd.exe
src/MsiNative.ps1          P/Invoke layer over msi.dll (compiled through Add-Type)
src/MsiReader.ps1          reads the Summary Information and the database tables
src/MsiCom.ps1             Windows Installer COM wrappers, used by the test generator only
src/MsiDiff.ps1            diff engine and the flattened file view
src/ReportHtml.ps1         HTML rendering
src/ReportMarkdown.ps1     Markdown rendering
src/ReportConsole.ps1      terminal summary
tests/New-TestMsiPair.ps1  generates a pair of test packages with known differences
```

## Smoke test

```powershell
.\tests\New-TestMsiPair.ps1
.\Compare-Msi.ps1 .\tests\out\DemoApp-1.0.msi .\tests\out\DemoApp-1.1.msi `
    -HtmlReport .\tests\out\diff.html -MarkdownReport .\tests\out\diff.md
```

The generator builds two packages with predefined differences: a changed product
version, ProductCode and Manufacturer, an added and a removed property, an added and a
removed file, changed stream content in the `Binary` table, a new `LaunchCondition`
table, a changed and a removed registry entry, and shifted version bounds in the
`Upgrade` table. The expected result is `+1 / -1 / ~3` for properties, `+1 / -1 / ~1`
for files, `+2 / -2` for `Upgrade`, and exit code 1.

With `-SignificantOnly` on the same pair, files should come out as `+1 / -1 / ~0`,
properties as `+1 / -1 / ~1` (`Manufacturer` alone), Summary Information should drop
from 4 changed fields to 3 (`Comments` is excluded), and the `MsiFileHash` and
`Upgrade` tables should move to "unchanged".

There is no reason to install these packages and you should not: they contain only a
database, with no real files or installation sequences.

## Implementation notes

- Every source file is plain ASCII, and both reports are written as UTF-8 with a BOM.
  Keep sources ASCII-only: Windows PowerShell 5.1 reads a BOM-less script as ANSI, so
  non-ASCII characters in string literals would break the parser.
- Open failures print the original Windows / Windows Installer text (and the numeric
  code), not a guessed diagnosis. `MsiOpenDatabase` reports a locked file, a missing
  file and a file that is not a database all as `ERROR_OPEN_FAILED`; when that happens
  the file is opened once more with a share-restricted handle so that a lock surfaces
  as the file system's own sharing-violation message.
- String comparison is case-sensitive, because case is significant for MSI identifiers.
- Table rows are matched by the primary keys stored in the database. When a table has
  no keys, matching falls back to the full set of columns and any change shows up as a
  removed/added pair.
- Files are matched by target path rather than by the key of the `File` table, so
  renaming a key while keeping the install path produces no false differences.
- The `msi.dll` access layer is compiled on first run through `Add-Type`, which adds
  about a second to process startup. The compiler ships with the .NET Framework and
  needs no separate installation.
- Cab archives and the contents of packaged files are not unpacked. A payload change is
  visible through the `MsiFileHash` table and the `FileSize` and `Version` fields.
- Transforms (`.mst`) and patches (`.msp`) are not applied: the databases are compared
  as they are.
